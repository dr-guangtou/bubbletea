UCD Reference Review Workbench

Summary

Build a local, single-reviewer web application for examining the complete reference set of:

  • 680 canonical objects classified as confirmed ultra-compact dwarf galaxies (UCDs) under confirmation_rules_v1; and
  • 44 objects from the Saifollahi et al. (2021) high-probability candidate table.

The tool will combine two-scale Legacy Survey imaging with literature provenance, Gaia measurements, host-galaxy context, Legacy Survey catalog measurements, and external contaminant-catalog evidence. It will record auditable visual observations, coordinate-correction proposals, and a manual decision about whether each confirmed UCD belongs in a clean positive design reference for deriving detailed UCD selection rules from combined Gaia and Legacy Survey measurements.

The application is a review and evidence-management system. It must never alter the canonical literature database, silently replace an object's coordinates, invent an unknown host, treat catalog membership as physical truth, or automatically remove an object from the positive design reference.

Scientific context

The current mosaic figures are useful for rapid comparison but are insufficient for source-by-source diagnosis. Important problems include:

  • the apparent source can be displaced from the literature coordinate;
  • host-galaxy light or structure can dominate a small cutout;
  • the source can be too faint for a reliable visual judgment;
  • nearby objects or image artifacts can confuse the interpretation; and
  • the expected appearance depends on host distance, because a nearby UCD may be visibly resolved while the same physical object would appear point-like farther away.

For this reason, “resolved” is an observation rather than an automatic contamination label. The interface must display it beside host distance and physical scale. The design-reference decision remains a separate human judgment supported by all available evidence.

The 44 Saifollahi high-probability objects remain candidates. They will be reviewed with the same interface but cannot enter the confirmed positive design reference. Their output is a separate follow-up-priority pool.

Legacy Survey catalog measurements

data/literature/catalogs/ucd_legacy_reference_tractor_matches_v1.csv

The Tractor profile type describes how the survey pipeline fit the light. PSF does not prove that a source is a star, and an extended profile does not prove that it is a background galaxy.

Two Legacy Survey image scales

Keep the existing compact view and prefetch one wider view for every target, except the 17 objects whose compact image is already a viewer-placeholder tile:

View Pixels Pixel scale Field width Purpose
Compact 64 × 64 0.262 arcsec/pixel 16.768 arcsec Central morphology and centering
Wide 256 × 256 0.262 arcsec/pixel 67.072 arcsec Neighbors, host light, and local context

Use the Legacy Survey DR10 three-color JPEG endpoint with the frozen literature coordinate as the requested center. Reuse verified existing compact images. Record the exact URL, coordinate, layer, dimensions, pixel scale, byte count, digest, content type, retrieval outcome, and image-content outcome for both scales.

A valid JPEG does not prove useful imaging. Preserve at least these content states:

  • nonuniform_image_content
  • viewer_placeholder_tile
  • unavailable_or_non_jpeg
  • unusable_wrong_dimensions

Do not automatically recenter an image on a catalog source. A mismatch between the literature coordinate and the visible source is evidence the tool is intended to record.

Gaia source preparation

For every target, preserve two distinct evidence paths:

  1. an accepted exact Gaia source identifier from the canonical literature evidence;
  2. diagnostic Gaia neighbors found by position.

Retrieve all Gaia DR3 sources within 5 arcseconds of every literature coordinate. Five arcseconds is a diagnostic search radius, not an association rule. Retain every neighbor and calculate its separation and position angle. Never automatically assign the nearest neighbor as the counterpart.

For accepted identifiers and positional neighbors, retrieve:

  • source identifier and ICRS coordinates;
  • G, BP, and RP magnitudes and fluxes where available;
  • raw BP/RP flux-excess factor;
  • parallax and uncertainty;
  • proper motion in both axes and uncertainties;
  • the proper-motion correlation needed for the combined significance calculation;
  • RUWE;
  • astrometric excess noise and its significance;
  • image-parameter multi-peak fraction;
  • image-parameter odd-window fraction;
  • duplicated-source status;
  • astrometric parameters solved;
  • visibility periods and observation counts where available;
  • Gaia classification probabilities; and
  • Gaia QSO-candidate, galaxy-candidate, and non-single-star membership.

Compute absolute parallax significance as abs(parallax) / parallax_error only when the uncertainty is finite and positive. Compute the two-dimensional proper-motion significance using the full covariance matrix, not by adding independent axis significances. Store raw inputs beside derived values.

Query all Gaia DR3 non-single-star solution tables used by the existing benchmark. Record which table contains a source and the published solution/model type. A source without an accepted Gaia identifier can only have positional-neighbor NSS evidence; it cannot be called an NSS catalog member of the UCD itself.

External catalog preparation

Use exact Gaia identifiers where the catalog supports them. Also perform bounded positional searches around every literature coordinate so objects lacking an accepted Gaia identifier remain diagnosable.

Every association must record:

  • catalog name and release;
  • catalog source identifier;
  • exact-identifier or positional-neighbor match basis;
  • catalog coordinates;
  • angular separation;
  • class or candidate label;
  • redshift and uncertainty where available;
  • catalog-specific measurements relevant to morphology or classification; and
  • provenance registry entry.

At minimum, integrate:

  • Gaia DR3 QSO candidates;
  • Gaia DR3 galaxy candidates;
  • Gaia DR3 non-single-star solution tables;
  • Quaia G < 20;
  • Gaia morphology galaxies with Sérsic fits; and
  • the local SDSS DR16 spectroscopic galaxy/QSO reference.

Exact identifier membership is stronger than a positional neighbor. The interface and exports must never collapse them into one Boolean flag.

Host-association register

Create a versioned host-association register with one row per canonical object and one of these states:

  • verified_unique_host
  • published_environment_only
  • ambiguous_host
  • host_unavailable

Normalize published host names only through reviewed aliases. Do not select the nearest galaxy automatically. For a verified unique host, preserve:

  • canonical host name and aliases;
  • host coordinates;
  • host-table row identifier;
  • adopted distance and distance source;
  • absolute K-band magnitude;
  • logarithmic K-band luminosity;
  • literature-coordinate angular separation;
  • projected separation at the adopted distance; and
  • parsecs per arcsecond.

For published_environment_only, show the published cluster/group text and source-level distance evidence, but do not calculate a galaxy-specific projected separation or attach one galaxy's luminosity. For ambiguous or unavailable hosts, leave derived host quantities missing and preserve an explanatory note.

Host assignments are scientific evidence and must be audited before the application uses them. Any later correction needs a new register version rather than an in-place edit without provenance.

Review-input bundle

Produce a compact, application-ready bundle rather than having the web server scan large FITS files or query remote services during review. The bundle must include:

  • one object row per canonical object;
  • all literature provenance associations;
  • accepted and diagnostic Gaia sources;
  • all Legacy Survey associations;
  • all external-catalog associations;
  • host associations;
  • image manifests for both scales; and
  • link templates or complete URLs.

Create a manifest containing input hashes, external file hashes, query text, match radii, retrieval dates, row counts, software command, output hashes, validation checks, and the review-bundle version.

Application architecture

Technology

Implement a localhost-only Flask application with vanilla HTML, CSS, and JavaScript.

  • Add Flask through uv; do not use pip, conda, or another package manager.
  • Bind only to 127.0.0.1 by default.
  • Do not add accounts, remote authentication, cloud storage, or public deployment in version 1.
  • Serve the prepared object bundle and cached images locally.
  • Store review state in a small external SQLite database.
  • Export compact CSV and JSON artifacts for version control.

The application should use a restrained observatory-console visual design: a dark neutral background, image-dominant layout, compact evidence tables, clear typography, high-contrast coordinate markers, and colorblind-safe status colors. Avoid decorative animation that distracts from image diagnosis.

Startup contract

Provide one documented command that:

  • resolves external data through BUBBLETEA_EXTERNAL_DATA;
  • validates the input manifest and required images;
  • opens or creates the review database; and
  • starts the server on localhost.

The server must refuse to start if the review bundle's recorded input hashes do not match the files on disk. A command-line option may allow read-only inspection of an older review database but must not silently migrate or rewrite it.

Review storage

The review SQLite database belongs under:

$BUBBLETEA_EXTERNAL_DATA/bubbletea/ucd_visual_review_v1/reviews/

Every save creates an append-only revision. Do not update or delete earlier revisions. Store:

  • review database schema version;
  • review-input bundle version and digest;
  • canonical object identifier;
  • UTC timestamp;
  • prior revision identifier;
  • all visual evidence states;
  • image usability;
  • design-reference or follow-up decision;
  • required reason and notes;
  • coordinate proposal, if any; and
  • client revision used for optimistic concurrency control.

The application is designed for one reviewer, but it must still prevent two browser tabs from silently overwriting one another. Reject a save if the submitted parent revision is no longer current and show the newer saved revision to the user.

Host or environment panel

Raw values must remain available even when the interface summarizes them as warnings.

External-catalog panel

Group evidence by catalog. For each result show catalog role, source identifier, class/candidate label, redshift where available, exact-identifier versus positional match basis, and separation.

Use explicit wording such as “Gaia galaxy candidate,” “Quaia QSO candidate,” “SDSS spectroscopic galaxy,” or “Gaia positional neighbor with an NSS solution.” Do not use a generic “contaminant” label that erases the evidence type.

Review model

Four-state visual evidence

Use a four-state segmented control for each visual observation:

  • not_reviewed
  • yes
  • no
  • uncertain

Require these seven observations for every usable image:

  1. resolved
  2. off_center
  3. close_to_host_light
  4. too_faint_to_judge
  5. blend_or_nearby_source
  6. image_artifact
  7. star_forming_or_young_cluster_appearance

Definitions:

  • Resolved: The central source appears broader or structurally extended relative to nearby point sources. This is not automatically negative; interpretation depends on distance and image quality.
  • Off-center: The likely intended object is visibly displaced from the literature coordinate crosshair.
  • Close to host light: Host-galaxy light, a galaxy halo, dust, or visible host substructure materially affects the cutout. This is distinct from a measured projected host separation.
  • Too faint to judge: The source is present weakly or not detected well enough to decide its morphology or centering reliably.
  • Blend or nearby source: A neighbor overlaps the source or is close enough to compromise visual or catalog measurements.
  • Image artifact: Saturation, diffraction, missing coverage, seams, unusual color patches, placeholder output, or another imaging problem compromises interpretation.
  • Star-forming or young-cluster appearance: The source appears associated with visible star-forming structure or irregular compact emission. Color alone cannot assign this observation.

Provide an image-usability field with:

  • not_reviewed
  • usable
  • partly_usable
  • unusable

An unusable image may complete through an explicit unusable-image path. In that path, visual flags may remain not_reviewed; the final design-reference decision must be hold, and the reviewer must provide a reason.

Notes

Provide:

  • one concise evidence note associated with visual flags;
  • one optional general comment; and
  • a required decision reason for exclude, hold, or candidate exclude / hold hold.

The interface should encourage factual descriptions such as “central source is 1.2 arcseconds east of the literature crosshair” rather than unsupported physical conclusions.

Coordinate-correction proposals

When off_center is yes or uncertain, require one of:

  • select an accepted or diagnostic Gaia source;
  • select a Legacy Survey association;
  • enter a manual ICRS RA and Dec; or
  • state that no corrected coordinate can yet be proposed.

Store:

  • proposed RA and Dec;
  • proposal source type and source identifier;
  • separation from the literature coordinate;
  • supporting note;
  • UTC time; and
  • review revision identifier.

A proposal is exported for a separate provenance audit. It must never update the canonical object or trigger automatic image recentering.

Confirmed-UCD design-reference decision

For confirmed UCDs, record one manual state:

  • not_reviewed
  • include
  • exclude
  • hold

exclude and hold require a reason. include may coexist with a positive visual flag, because a nearby real UCD can be resolved or close to host light. In that case, show a confirmation warning so inclusion is intentional.

An object cannot enter the clean design-reference export unless:

  • its image is usable or partly usable;
  • all seven visual observations have been answered;
  • any off-center evidence has a completed coordinate-proposal response;
  • its design-reference decision is include; and
  • the current review revision passes server-side validation.

The tool does not automatically translate any single catalog flag into exclusion.

Candidate follow-up decision

Saifollahi candidates use the same three decisions as confirmed UCDs:

  • not_reviewed
  • include
  • exclude
  • hold

A candidate's include means "a good candidate to keep in the follow-up pool", not a promotion to confirmed. Candidates cannot enter the confirmed positive design-reference export even when marked include. Their review output remains a separate follow-up pool with all provenance and evidence retained.

Completion rules

A usable-image review is complete only when:

  • image usability is answered;
  • all seven visual observations are answered;
  • an off-center proposal response is complete when required;
  • the cohort-appropriate final decision is answered; and
  • a required reason is present.

Review completion and design-reference eligibility are different. An excluded or held object can have a complete review.

Local API

Provide these minimum routes:

  • GET /api/summary
  • GET /api/objects
  • GET /api/objects/{canonical_object_id}
  • GET /api/objects/{canonical_object_id}/history
  • GET /api/images/{canonical_object_id}/{compact|wide}
  • POST /api/objects/{canonical_object_id}/reviews
  • POST /api/export

GET /api/objects must support filtering, sorting, pagination, and stable navigation. The object-detail response must group provenance, Gaia, host, Legacy Survey, external catalogs, images, links, and current review state rather than returning one ambiguous flat namespace.

The save endpoint must validate:

  • allowed four-state values;
  • allowed image-usability values;
  • cohort-specific final decisions;
  • required reasons;
  • required coordinate-proposal response;
  • candidate prohibition from confirmed design-reference inclusion;
  • parent revision currency; and
  • canonical object membership in the frozen input bundle.

Return structured validation errors that the interface can place beside the relevant field.

The clean positive design-reference export must contain only confirmed objects with current include decisions that satisfy every eligibility rule. It must link back to the review revision and all source evidence; it must not become a replacement canonical literature table.

Acceptance criteria

Scientific integrity

  • The canonical literature database and frozen input tables remain byte-identical during review.
  • Exact-identifier and positional-neighbor evidence cannot be confused in the UI or exports.
  • Unknown or ambiguous hosts never acquire calculated host luminosity or projected separation.
  • Candidate status never becomes confirmed status through review.
  • Saifollahi candidates never enter the confirmed positive design-reference export.
  • Coordinate proposals appear only as proposals and never change canonical coordinates.
  • Catalog membership and fitted profile types remain evidence, not automatic truth labels.
  • Incomplete reviews cannot enter the clean positive design-reference export.

Image and geometry validation

  • Every image endpoint serves the file recorded for the requested object and scale.
  • Image dimensions and digests match the image manifest.
  • Literature coordinates map to the image center within numerical rendering tolerance.
  • Gaia, Legacy Survey, and proposal overlays reproduce recorded separations and position angles using the documented pixel transformation.
  • Placeholder and unavailable images are never labeled clean automatically.

Persistence and API behavior

  • Restarting the server preserves every saved revision.
  • Saving creates a new revision and retains the previous one.
  • A stale parent revision produces a conflict rather than overwriting new work.
  • Server-side validation rejects invalid flag states, incomplete required evidence, or cohort-incompatible final decisions.
  • Exporting does not change review state.

Interface behavior

  • Search, filters, sorting, and filtered previous/next navigation work on all 724 objects.
  • Both image scales load and overlays can be toggled independently.
  • Zoom, pan, reset, keyboard save, history, unsaved-change warnings, and external links work in the supported browser.
  • Missing measurements display as unavailable rather than zero.
  • Confirmed and candidate progress remain visibly separate.

Reproducibility and code quality

  • Every generated data product has a manifest with provenance and hashes.
  • Data-preparation and validation scripts are standalone and use paths from scripts/config.py.
  • All dependencies are managed through uv.
  • Ruff, pre-commit, data validation, API checks, export checks, and git diff --check pass.
  • No file larger than 10 MB, database file, FITS file, or downloaded image cache is committed.

Measured performance

Benchmark rather than estimate:

  • startup and manifest-validation time;
  • object-list response time;
  • object-detail response time;
  • review-save latency;
  • filtered navigation latency; and
  • full export time.

Record the commands, hardware context, full 724-object measurements, and acceptance thresholds chosen from the measured pilot. Do not claim responsiveness before it has been measured.

  11. Run automated validation and a browser smoke test.
  12. Conduct a 12-object pilot spanning all validation fixtures.
  13. Stop for project-lead review of the interface, visual definitions, host handling, and exports before opening all 724 objects for production review.
  14. After review approval, freeze the production review version and begin the full source-by-source assessment.

Frozen assumptions and decisions

  • Version 1 is local, single-user, and bound to localhost.
  • The application uses Flask with plain HTML, CSS, and JavaScript.
  • Review state is stored in an external SQLite database with append-only history.
  • No reviewer identity is recorded; the workbench is a single local user.
  • Image scales are 16.768 and 67.072 arcseconds at 0.262 arcseconds per pixel.
  • Visual observations use not_reviewed, yes, no, and uncertain.
  • The required visual set has seven observations.
  • Host-derived properties require a separately verified unique host.
  • Exact identifiers and positional neighbors are separate evidence types.
  • Coordinate corrections are proposals for later provenance audit.
  • Design-reference membership is manual and separate from evidence flags.
  • Only confirmed UCDs can enter the positive design reference.
  • Saifollahi candidates and confirmed UCDs share the same include/exclude/hold decisions; a candidate include never enters the confirmed design reference.
  • The clean positive design reference supports deriving detailed UCD selection rules from combined Gaia and Legacy Survey measurements; it is not model training.
  • This workbench reviews only the literature confirmed UCDs and high-probability candidates. The later candidate-selection review tool is a separate deliverable.
  • The 17 known viewer-placeholder objects receive only the compact image; the wide image is not retrieved for them.
  • Host-association policy (2026-08-13): a single published galaxy name resolves to verified_unique_host; a published cluster/group name resolves to published_environment_only and adopts the cluster/group distance; a galaxy pair (X/Y) resolves to the named group; an empty host field resolves from the source publication's documented environment rather than remaining unknown.
  • The 13 Voggel 2020 candidate stripped-nucleus / luminous-globular-cluster objects are excluded from the confirmed positive design reference (see data/literature/sources/confirmed_ucd_design_reference_exclusions_v1.json).
  • Adopted cluster distances: Virgo cluster 16.5 Mpc, Centaurus cluster 43.0 Mpc, Hydra I (NGC 3311) 50.7 Mpc, NGC 5128 3.8 Mpc. The register is data/literature/catalogs/host_association_register_v1.csv.
  • A complete review requires all applicable visual evidence and a final decision.
  • No review action changes literature classification, canonical coordinates, host identity, selector output, radial profiles, or source provenance.
